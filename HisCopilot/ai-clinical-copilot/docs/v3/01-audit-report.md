## 3. 性能 / 可用性

| # | 发现 | 根因 | 状态 |
|---|---|---|---|
| P1 | 语音转写 49 秒、OCR 22–53 秒，手机端报 503/500 | llama.cpp 线程数（128）超过容器 CFS 配额导致严重争抢；加上 Next 代理 30 秒超时把长请求掐断 | ✅ ASR/OCR 服务按有效 CPU 配额设置线程（ASR ≈1 秒、OCR ≈11 秒）；🔧 API 立即返回任务 ID、前端轮询，代理超时不再相关 |

## 4. 工程质量

- `app.py` 3044 行单体、`AnalyzePanel.tsx` 1466 行、重复的 orchestrator 目录；SQLite 未开外键、`journal_mode=delete`；无迁移体系。
  → 🔧 `server/` 分层（api / domain / db / security / safety / ai / jobs）、版本化迁移（checksum 不可变 + 迁移前自动在线备份）、外键+WAL+busy_timeout、统一错误格式与 request_id、哈希链审计日志。
- 前端：`/patients` 页面被错误套用患者布局（`startsWith("/patient")`）；无统一应用框架；各页重复加载。
  → 🔧 新 `apps/web`：`(staff)` 路由组共用一个常驻应用外壳（侧栏/顶栏不重载），患者端 `/p/*` 独立极简布局。
