## 4. 未验证 / 局限（不要当作已通过）

- **真实手机**、真实弱网、真实 HTTPS 下的录音体验：只在桌面 Chrome（手机视口 + 虚拟麦克风）验证了 MediaRecorder 路径与"调用手机录音"降级文案。
- **预约 → 到诊登记**的完整浏览器路径（API 级已测）。
- **性能/压力**：只做了并发正确性测试，没有持续压测；27B 串行队列下多医师同时起草方案的排队时间未测。
- **医学内容正确性**：测试只判断结构与安全属性（引用有效、候选数量、药味数量与数值剂量、规则是否执行、过敏药是否被规则标出），**不评判诊断是否临床正确**；规则库覆盖有限（见《后续建议》）。
- **旧系统到 v3 的切换**未执行（见运行手册）；v3 当前在 8011/3100 并行运行，旧系统仍在 8001/3000。
- PDF 版面只验证"可生成且非空"，未做视觉审阅。

## 5. 真实模型端到端（`tests/e2e/live_models.js`，无任何替身）

环境：主栈 :8011/:3100，模型服务 7870 (Qwen3.8-27B, GPU1) / 7871 (ShizhenGPT-7B, GPU1) / 7872 (Qwen3-ASR, CPU) / 7875 (PaddleOCR-VL, CPU)。素材：真实录音、真实检验单、真实舌象照片。脚本只判断**结构与安全属性**，不判断临床是否正确。

| 阶段 | 耗时 | 结果 |
|---|---|---|
| 三个文件上传并处理（ASR + OCR + 舌象入库） | 33 s | ASR：“你好，这里是丰西堂中医医院。”；OCR 解析出 23 个检验项，**全部以“未核对”开始** |
| 预分析（舌象 VLM 25 s + 西医 27B 98 s + 中医 7B 14 s + 综合 43 s） | 156 s | 4 个模块均成功；西医 3 个鉴别诊断（2 型糖尿病 / 尿崩症 / 早期慢性肾病），中医 2 个证候（气阴两虚 / 阴虚火旺），每条都带置信度、引用、缺失信息；所有引用都指向真实事实 |
| 统筹方案（27B） | 137 s | 草稿；1 个中药方（9 味，克数均为正数）、1 个西药（二甲双胍，因不在目录被规则标为“需确认”）、2 个治疗项目（均为“待审核”）；安全预检已执行 |

**这次真实运行暴露并推动修复的问题：**
1. 第一次运行时 27B 对西医模块返回了**合法 JSON 但没有 `differentials` 数组**（用同样的提示词单独再调一次是正常的，说明是偶发形态）。当时管线正确地“只失败该模块、不编造诊断、整体标 partial”，但**没有保留模型原文，无法排查**。已改为：接受常见键名变体、缺失时带提醒重试一次、失败时保存模型原文节选（界面“运行详情”可展开）。修复后复跑：西医模块一次成功（未触发重试）。
2. 一次选 3 个文件只有第一个被上传（第二、三个被单飞锁静默丢弃）→ 上传改为排队。

**真实输出里值得人工留意的现象（不是测试失败，而是医师审核层存在的理由）：**
- **OCR 名称会有误识**：数值读对了，但名称出现 “血清内氢酸氨基转移酶”（应为丙氨酸氨基转移酶/ALT）、“蛋白”（应为白蛋白）、“肌酐测定 (酶促动力学”（括号被截断）。因此检验项必须与原图并排、逐项核对（界面已这样做，未核对的数值会被 AI 标注）。后续可加检验项目名称词典做规范化（见《后续建议》）。
- **AI 方案可能临床上不妥**：这位患者空腹血糖 4.88 mmol/L（正常），AI 仍在统筹方案中建议启动二甲双胍；同一次分析的综合评估却写的是“需优先排查 2 型糖尿病（完善 HbA1c/OGTT）”。系统把它放在“草稿 + 待医师确认 + 规则预检”里，没有自动生效——这正是“医师保有最终决定权”的设计目的，但也说明**不能把 AI 方案当作结论**。
