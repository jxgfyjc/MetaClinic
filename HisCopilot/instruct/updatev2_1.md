# 象元 AI 诊疗：核心体验与闭环质量升级

基于现有代码增量开发，不推倒重写。将整个产品统一命名为「象元 AI 诊疗」，把现有系统打磨成可独立运行、数据持久化、流程完整的中西医结合门诊系统。

## 1. 综合诊疗：只输出一份最终方案

保留西医分析、中医辨证作为内部独立分析能力，但最终必须由综合决策模块整合两者，形成**一份统一的诊断评估和综合治疗方案**，不能分别生成两份互相割裂的处方与治疗计划。

医生先审核、选择或修改最终诊断，再根据已确认的诊断异步生成对应的统一方案，包含：

* 药物：西药、中成药、中药饮片及经方，支持选择、新增、修改、删除。
* 非药物治疗：仅在适用时推荐推拿、针灸、艾灸、物理治疗和康复。
* 辅助管理：生活方式、复诊和随访建议。

综合方案应协调中西医诊断，避免重复用药、相互矛盾或无关治疗。医生可以在一张统一表单中审核全部建议，分别管理不同治疗项目，并最终形成一份综合诊疗记录。

**推拿、针灸及理疗建议必须达到专业结构化程度**，根据适用的知识资料和临床规范输出具体穴位名称、定位依据、操作手法、方向或刺激方式、时长/次数、频率、疗程及禁忌提示。理疗应明确具体治疗方式与必要参数。信息不足或缺乏可靠依据时明确标注待医生确认，不得臆造穴位、操作参数或院内项目编码。

输出保持精炼，使用结构化字段和简洁理由，不生成冗长的教学文章。所有处方与治疗方案均须医生审核确认。

## 2. ASR 必须可诊断，彻底解决反复 500 的盲查问题

检查现有录音、上传、音频预处理、ASR 调用和文本后处理全链路，禁止只捕获异常并返回通用的「ASR 不可用」。

每次请求生成统一 `request_id`，记录各阶段耗时、HTTP 状态、异常类型、完整服务端堆栈、模型端点和可安全记录的错误响应摘要。

针对音频记录必要的诊断元数据：文件大小、格式、编码、采样率、声道数、时长及预处理结果。区分录音权限失败、上传失败、格式不支持、音频解码失败、模型服务不可用、推理异常、CUDA/OOM 和后处理失败。

增加 ASR readiness/healthcheck 与最小音频测试入口。前端失败时展示明确的错误分类和 `request_id`，管理员可以按 ID 查询对应日志。语音转写必须真实调用现有本地模型，不能使用模拟文本掩盖错误。

日志默认不保存原始音频、患者完整病情文本或其他不必要的敏感内容；需要留存音频用于排障时必须有明确授权与保存策略。确保日志能定位根因，而不是记录空洞的「500」。

## 3. 全系统统一为「象元 AI 诊疗」

检查前端所有路由、页面、导航、标题、登录页、提示信息、图标及 README 等文档，统一使用「象元 AI 诊疗」品牌。

清理面向用户的 `Demo`、`Mock`、`Test Patient`、`演示功能` 等遗留字样、硬编码数据和假按钮。主界面应以真实新建患者和自定义病情为入口，支持患者手机端资料提交、医生端直接接诊、语音、检验报告和舌象上传。

不允许通过隐藏标签来冒充真实业务：Mock HIS 相关实现可以保留，但在系统配置或集成状态中必须如实标记当前未接入真实 HIS。本系统 V1.0 应独立完成患者建档、接诊、病历、诊断、方案审核、记录保存和随访闭环。

## 4. 验收与约束

使用全新虚构病例实际验证：

患者输入病情及语音 → 上传检验与舌象 → 医生收到资料 → 真实 AI 分析 → 医生确认诊断 → 生成一份统一综合治疗方案 → 修改处方与治疗项目 → 保存诊疗记录 → 创建随访。

另外单独验证 ASR 成功、格式错误、服务关闭和推理异常，确认每次失败都能定位到具体阶段。验证图片确实送入视觉服务，OCR 结果进入临床上下文，业务数据在 API 重启后仍然存在。

先审计现状，再实施并回归测试。更新 `docs/quality-upgrade-status.md`，记录修改、错误根因、测试证据和遗留问题。

不下载新模型、不训练、不更换现有模型，不重写后端，不创建新的 Python 环境，不修改 GPU 分配，不碰 8000/8188 及既有 ComfyUI、aivideo，不接真实 HIS。所有 AI 结果必须来自真实模型调用。
