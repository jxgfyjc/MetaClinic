# 任务：以 his-functional-blueprint.md 为模板，重构现有系统的整体产品框架

你是本项目的 Principal Product Engineer。

当前项目已经跑通真实本地 AI 模型、FastAPI、SQLite 持久化、医生审核、处方状态机、Mock HIS、随访与故障降级。

项目根目录中有 `his-functional-blueprint.md`，这是甘草云管家的功能蓝图。本轮以它为主要产品结构参考，建设完整、统一、可操作的医院门诊管理界面。

## 1. 先分析现有项目与蓝图

读取功能蓝图和现有代码，梳理：

* 参考产品的导航、页面层级、核心工作流、业务实体。
* 现有前端路由、组件、API、数据库和 AI 服务。
* 哪些页面可直接复用，哪些需要新建，哪些只能先做界面框架。

输出 `docs/ui-reconstruction-plan.md`，但不要停留在文档阶段，完成梳理后立即开发。

## 2. 建设整体产品框架

参考蓝图中的产品信息架构，按本院小型医院的实际需求进行取舍，至少规划：

* 医生工作台及今日待办
* 患者管理、患者档案与历史时间线
* 预约、挂号及接诊
* 医师工作站与临床诊疗室
* 病历管理、医案与处方模板
* 西药、中成药、中药饮片与院内协定方管理
* 推拿、针灸、艾灸、理疗及康复治疗项目
* 多医生个性化诊疗配置与个人经验库
* 药房与药品基础资料
* 随访、风险预警
* 知识库、员工权限、审计和基础报表

建立统一的侧边导航、页面标题、面包屑、搜索、表格、详情页、表单、抽屉和弹窗交互。

参考产品的菜单和业务组织方式，但根据本院需要设计自己的品牌、文案和视觉，不直接复制其受保护的源代码、商标或专有素材。

## 3. 保留现有 AI 核心

绝对不要推倒重写现有后端或替换已经跑通的模型。

保留：

* Qwen 临床分析
* ShizhenGPT 中医辨证
* 现有 AI Orchestrator 与异步任务
* 现有模型服务和 RAG
* SQLite Repository 与数据持久化
* 病历保存、医生审核、处方状态机
* Mock HIS、随访及故障降级

将现有 `/encounters/[eid]` 作为核心临床工作台，融入整体产品框架。

新增页面通过已有 API 或清晰的服务接口接入。禁止为了统一 UI 而修改已有接口契约、破坏真实模型调用或重置数据库。

## 4. AI 和个性化诊疗是产品特色

在诊疗室中统一展示：

* 西医病情分析和鉴别诊断
* 中医辨证与经典经方
* 舌象分析
* 医生个人风格和经验检索
* 西药、中成药、中药饮片候选
* 推拿、针灸、理疗、康复等综合治疗方案
* 知识依据、审核操作和随访建议

AI 建议、医生修改内容与正式医疗记录必须明确区分。所有处方和治疗方案都应经过医生审核；没有配置的药品编码、治疗项目和收费编码不得伪造。

## 5. 开发策略

先完成所有主要页面的整体布局、路由、导航和统一视觉，再逐步接通业务 API。

允许暂时用显式标注的 Demo 数据构建尚未接通的页面，但不得伪装成功能已经完成。优先完成医生工作台、患者档案、接诊、病历、处方和随访的真实数据链路。

不要一次性重写所有页面，不要为尚未启用的财务、商城、医保或供应链功能开发复杂后端。

## 6. 环境约束

不下载新模型、不训练、不创建新的 Python 环境，不改变 GPU 分配，不修改既有 ComfyUI 和 aivideo，不碰 8000/8188 端口。不接真实 HIS，不使用真实患者生产数据。

## 7. 验收标准

* 主要导航、路由和页面框架完整。
* 页面风格和交互一致。
* 医生可以从工作台进入患者、接诊和临床 AI 副驾。
* 现有真实模型分析和黄金路径仍然可用。
* 患者、病历、处方及随访数据仍可持久化。
* 未实现模块有明确标识，不存在大量死按钮或假业务。
* 更新 `docs/ui-reconstruction-status.md`，记录页面完成度、真实 API 接入情况、未完成功能及回归测试结果。

现在开始检查项目并实施。优先形成完整的产品框架和 UI，再逐步深化业务功能，不要只输出设计方案。
