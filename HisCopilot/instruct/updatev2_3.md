# 象元 AI 诊疗：诊疗数据模型与完整门诊闭环修复

请基于现有代码增量修复，不推倒重写。先检查患者、就诊、AI 输出、诊断、治疗方案、病历和处方的实际数据关系，再实施修复。

## 1. 统一诊断与综合治疗方案

多个 AI 诊断候选被医生接受后，只允许汇总形成一个本次就诊的「最终诊断列表」，不能每接受一个诊断就创建一份完整治疗方案。

医生完成诊断选择或修改后，针对全部已确认且相互兼容的诊断，统一生成一份综合治疗方案，整合西药、中成药、中药饮片、经方及适用的推拿、针灸、理疗、康复建议，避免重复用药和相互矛盾的治疗。

接受、修改或驳回诊断条目时，应实时同步更新最终诊断列表。诊断变化后，旧方案应标记为待重新审核或过期，不得静默沿用不匹配的处方。

综合治疗方案应保存为独立、可恢复的记录。医生修改和确认后，将最终内容用于生成正式病历和相应处方文书，而不是仅保存在 AI 分析页面中。

## 2. 明确正式病历、治疗方案与处方的关系

建立清晰的状态和关联：

`患者档案 → 本次就诊 → 病史与检查 → 最终诊断 → 综合治疗方案 → 医生确认 → 正式病历 / 电子处方 / 治疗医嘱 → 随访`

正式病历编辑器应自动汇总患者信息、本次主诉、现病史、既往史、过敏、检查结果、医生确认的诊断和治疗意见。医生可以继续编辑；保存时形成草稿，最终确认后保存正式记录、操作者与时间。

最终诊疗记录必须可以从历史就诊中重新打开，支持打印或 PDF 导出。电子处方单独持久化，包含患者、诊断、药品、规格、剂量、用法、数量和医师确认信息，支持查询、打印导出及后续药房查看。中药饮片与其他药物按适用规范生成相应处方文书。

## 3. 修复患者信息与就诊事实为空的问题

重点排查字段映射、API 请求与数据库写入，不要在前端用静态文本填补空值。

- 患者提交的姓名、性别、年龄必须写入患者档案。
- 主诉、现病史、语音转写和检查资料必须写入对应的本次就诊记录。
- 患者档案与就诊记录应通过稳定的 `patient_id` 关联。
- 页面必须展示真实保存的数据；对尚未填写的字段明确显示“未填写”，不得无故显示空白或虚构信息。

使用一份全新患者资料从患者端提交，再检查数据库、患者详情、今日接诊、临床工作台中的同一组字段是否完全一致。

## 4. 明确患者列表、今日接诊和临床诊疗室

三者是不同的业务入口：

- **患者列表**：以人为单位，每人只有一条长期患者档案入口。点击姓名进入该患者详情和历史就诊时间线。
- **今日接诊**：以就诊事件为单位，显示当天待接诊、接诊中、待确认和已完成的就诊记录。一个患者可以有多次就诊。
- **临床诊疗室**：针对某一个确定的 `encounter_id` 开展问诊、AI 分析、诊断确认、治疗方案编辑和处方处理。

点击患者不能默认跳到不明确的就诊列表。患者详情应分别显示历史就诊，并提供明确的“查看本次就诊”和“新建就诊”操作。

重新梳理导航、按钮与路由，避免“今日接诊”和“临床诊疗室”按钮重叠、粘连或指向同一错误页面。

## 5. 患者端与医生端

患者端只保留资料采集表单，包括个人信息、主诉、现病史、语音、检查报告和舌象上传。不得展示 AI 治疗、诊断候选、处方或内部推理。

医生端独立查看患者资料、AI 预分析和接诊状态，并完成诊断、治疗方案、病历与处方的审核确认。所有权限在后端校验。

## 6. 验收

使用全新虚构患者实际测试：

患者登记 → 患者列表出现该患者 → 今日接诊出现独立就诊记录 → 医生进入对应诊疗室 → AI 分析 → 接受多个诊断条目 → 只生成一份综合治疗方案 → 修改药物和治疗项目 → 保存正式病历 → 生成并导出处方 → 创建随访。

验证所有数据关联正确，刷新和重启 API 后记录仍然存在；页面之间不会串患者、串就诊或产生重复方案。

更新 `docs/closure-audit.md` 和 `docs/closure-status.md`，列出发现的根因、修复内容与真实测试结果。优先复用现有数据库和 API，不破坏已跑通的 Golden Path，不使用硬编码数据伪装修复完成。
