# V1.0：独立中西医门诊系统 + 双入口问诊 + AI 临床副驾

你是本项目的 Principal Product Engineer + AI Architect。请基于当前代码仓库增量开发，不要推倒重写。

## 一、产品目标

将现有 AI Demo 升级为一套**自成体系、可独立运行的中西医门诊系统 V1.0**。

系统拥有自己的患者档案、就诊记录、病历、检验资料、AI 分析、处方草稿、综合治疗方案和随访数据。现阶段不依赖真实 HIS 即可完成完整门诊流程。

原有 HIS 接口设计继续保留，通过独立 Adapter 预留未来接入能力，但本版不要求对接真实 HIS，也不能依赖 HIS 才能创建患者和完成接诊。

重点解决：用户可以自由输入任意病情，而不是只能体验预置患者；同时支持患者自主提交资料和医生直接采集病史两种模式。

## 二、两种病史采集入口

### 入口 A：患者自主问诊

提供手机优先的患者端，首页醒目展示「开始问诊」。

流程：

选择或创建患者档案 → 文字描述病情 / 语音录入 → 上传检验报告、病历及舌象图片 → 预览和修改 → 提交给医生。

要求：

* 语音按钮必须真实可用，接入现有本地 ASR，显示转写结果并允许编辑。
* 检验报告接入现有 OCR 服务；保留原图，并允许确认或修改识别结果。
* 舌象图片保存并关联本次就诊。
* 患者可以只填写部分资料，不得强制填写所有医学字段。
* 提交后真实保存至数据库，并出现在医生端「待接诊 / 新提交资料」列表。
* 展示提交状态和提交时间，医生可以打开查看全部内容。

### 入口 B：医生直接采集病史

医生无需等待患者提交资料，即可主动接诊。

流程：

搜索已有患者或新建患者 → 创建就诊 → 输入主诉与现病史 → 文字或语音录入 → 补充既往史、过敏史、当前用药和检验 → 自动整理病历草稿 → 启动 AI 分析。

医生端同样必须提供明显的麦克风按钮，并复用现有 ASR。

支持医生在问诊过程中持续补充、修改和保存资料。新增信息后允许重新分析，并保留历史运行记录。

## 三、统一临床工作流

两种入口最终汇入同一套患者档案和 Encounter 数据模型，禁止分别维护两套互不关联的数据。

统一流程：

患者资料采集 → 结构化临床上下文 → 自动生成病历草稿 → 医生选择诊疗模式 → 调用真实 AI → 生成治疗建议 → 医生审核和修改 → 保存正式病历及业务记录 → 创建随访。

医生可选择：

1. **西医方案**：病情分析、鉴别诊断、证据、信息缺口及检查建议。
2. **中医方案**：四诊信息、证候候选、辨证依据、治法、经典经方和中药候选。
3. **中西医综合方案**：整合上述分析，补充适用的推拿、针灸、艾灸、理疗、康复和随访建议。

继续使用现有 Qwen、ShizhenGPT、ASR、OCR、RAG 和 AI Orchestrator。所有 AI 输出必须来自真实模型调用，不得使用静态 JSON 冒充。

病历首先是可编辑草稿；处方和治疗方案必须经过医生审核。未经确认的 AI 建议不得直接变成正式医疗记录。

## 四、医生个性化诊疗

预留并实现最小可用的医生画像：

* 科室及擅长领域。
* 辨证分析偏好。
* 经典经方和院内协定方偏好。
* 组方与综合治疗偏好。
* 经医生确认的个人经验。

同一病例切换不同医生时，允许模型根据医生画像和相关经验调整分析重点及候选方案排序，但不能为了体现风格而编造不同诊断或忽略患者风险。

治疗项目与药品分开管理。推拿、针灸、理疗和康复使用独立的数据结构；没有真实院内项目资料时，不得伪造项目编码或收费信息。

## 五、先完成整体产品 UI

统一导航与页面风格，优先实现：

* 医生工作台及待接诊列表。
* 患者管理和患者纵向档案。
* 新建接诊与病史采集。
* AI 临床副驾与综合治疗方案。
* 病历编辑、处方审核和治疗建议审核。
* 知识库、医生画像及院内方药管理。
* 随访和风险预警。
* 基础系统管理与审计。

首页必须醒目提供两个入口：「患者自主问诊」和「医生直接接诊」。

优先实现医生端与患者端的完整体验，再逐步完善药房、收费、医保等扩展模块。尚未实现的模块必须明确标注，不允许用死按钮伪装可用功能。

## 六、系统与接口约束

1. 现有数据库是 V1.0 的业务事实源，核心数据必须持久化，重启后仍可恢复。
2. 继续复用现有 Repository、模型服务及 Mock HIS 代码，不大规模重构后端。
3. HIS Adapter 保留独立接口，本版使用自身业务服务，不连接真实 HIS。
4. 保留现有异步 AI 分析、任务状态、部分失败处理和处方幂等机制。
5. 当前约 240 秒的 AI 完整分析耗时仍需记录和后续优化，但不得阻塞产品框架开发；模块结果应在真实完成后尽早展示。
6. 不下载新模型、不训练、不更换模型、不创建新 Python 环境。
7. 不修改 GPU 分配，不触碰 8000/8188 端口及既有 ComfyUI、aivideo，不向公网发送患者数据。

## 七、最终验收

必须使用一个此前不存在的虚构病例，分别验证两条入口。

**患者入口：**

手机访问 → 输入任意新病情 → 录音转写 → 上传检验报告 → 提交 → 医生端收到资料 → 自动生成病历草稿 → AI 分析 → 医生审核 → 保存并创建随访。

**医生入口：**

医生直接新建患者与就诊 → 手动输入或语音采集 → 自动生成病历草稿 → 选择中医、西医或综合方案 → 调用真实模型 → 审核处方与治疗方案 → 保存记录。

最后验证数据库持久化、API 重启恢复、AI 故障降级和页面刷新恢复。

完成后生成 `docs/v1-status.md`，列出已实现功能、真实 API 接入情况、测试证据与未完成项。

先审计现有项目，再直接实施。不要只输出架构方案，不要等待所有扩展模块完成后才提供可运行系统。

**最终目标：一套可以脱离 HIS 独立完成门诊流程的 V1.0，而不是多个功能拼接的 Demo。**
